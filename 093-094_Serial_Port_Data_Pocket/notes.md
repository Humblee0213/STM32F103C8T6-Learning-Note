# 29 — USART串口通信：串口收发 HEX 数据包与文本数据包

> 资料说明：本节对应江协科技《STM32入门教程-2023版》的 **[9-5] 串口收发HEX数据包 & 串口收发文本数据包**。由于无法直接取得视频完整字幕与逐帧画面，本文依据可访问的分集信息、前后课程上下文，以及 STM32F103 USART 的官方资料整理；核心代码属于标准外设库风格的参考实现，并非逐字抄录的视频源码。

## 实验概述

前面的串口实验已经能够发送、接收单个字节和字符串，但真实项目中的串口通信通常不能只依靠“收到一个字节就立即处理”。当连续传输多个参数或命令时，接收端还需要判断：

1. 一帧数据从哪里开始
2. 一帧数据在哪里结束
3. 当前接收的是数据还是控制字符
4. 数据是否完整
5. 接收完成后应当执行什么操作

本节通过两个实验建立最基础的串口应用层协议：

1. **HEX 数据包实验**：使用固定包头、固定长度数据区和固定包尾传输二进制数据。
2. **文本数据包实验**：使用 `@` 作为包头、`\r\n` 作为包尾，接收可直接阅读的命令字符串。
3. **文本命令控制实验**：解析 `LED_ON`、`LED_OFF` 等命令，并通过串口返回执行结果。

本节核心流程如下：

```text
USART 接收字节
      ↓
RXNE 中断读取数据寄存器
      ↓
状态机判断包头、数据区和包尾
      ↓
完整数据写入接收缓冲区
      ↓
置位接收完成标志
      ↓
主循环解析数据并执行功能
```

## 通信协议设计

### 1. HEX 数据包格式

本实验使用固定长度数据包：

```text
包头        数据区                         包尾
0xFF        Data0 Data1 Data2 Data3        0xFE
```

完整数据包共 6 字节：

| 字段 | 长度 | 示例 | 说明 |
|---|---:|---:|---|
| 包头 | 1 字节 | `0xFF` | 标识一帧 HEX 数据开始 |
| 数据区 | 4 字节 | `0x01 0x02 0x03 0x04` | 保存需要传输的二进制数据 |
| 包尾 | 1 字节 | `0xFE` | 标识一帧 HEX 数据结束 |

### 2. 文本数据包格式

本实验使用可变长度文本包：

```text
包头        文本数据                  包尾
'@'         LED_ON                    "\r\n"
```

串口助手发送示例：

```text
@LED_ON\r\n
@LED_OFF\r\n
```

| 字段 | 内容 | 说明 |
|---|---|---|
| 包头 | `@` | 标识文本命令开始 |
| 数据区 | `LED_ON` | 需要解析的命令字符串 |
| 包尾 | `\r\n` | 回车加换行，标识文本命令结束 |
| 字符串结束符 | `\0` | 由接收程序补充，便于使用 `strcmp()` |

## 硬件连接

以 STM32F103C8T6 最小系统板、USB-TTL 模块和江协科技常用实验接线为例：

| 器件 | 对应引脚 | 说明 |
|---|---:|---|
| USART1_TX | PA9 | STM32 发送端，连接 USB-TTL 的 RX |
| USART1_RX | PA10 | STM32 接收端，连接 USB-TTL 的 TX |
| USB-TTL GND | GND | 必须与 STM32 共地 |
| LED1 | PA1 | 常见课程接线为低电平点亮，具体以实际原理图为准 |
| Key1 | PB1 | HEX 数据包实验中用于触发发送 |
| OLED SCL | PB8 | 软件 I²C 时钟线，辅助显示数据 |
| OLED SDA | PB9 | 软件 I²C 数据线，辅助显示数据 |
| ST-Link V2 | PA13、PA14、GND、3.3V | SWD 下载与调试 |

> 注意：USB-TTL 与 STM32 的串口信号必须交叉连接，即 `TX → RX`、`RX → TX`，并且必须共地。USB-TTL 的逻辑电平应与 STM32 的 3.3V 系统兼容。

## 核心代码

### 1. Serial.h

```c
#ifndef __SERIAL_H                                                     // 判断串口头文件是否尚未被包含，防止重复定义
```

### 2. Serial.c：全局变量与 USART1 初始化

```c
#include "stm32f10x.h"                                                 // 引入 STM32F10x 标准外设库，提供 RCC、GPIO、USART 和 NVIC 接口
#include "Serial.h"                                                    // 引入本模块头文件，保证函数声明、宏和变量类型保持一致

uint8_t Serial_TxPacket[SERIAL_HEX_DATA_LENGTH];                        // 定义 HEX 发送数据区数组，主循环可修改其中的 4 个数据字节
uint8_t Serial_RxPacket[SERIAL_HEX_DATA_LENGTH];                        // 定义 HEX 接收数据区数组，中断状态机完成一帧后写入数据
uint8_t Serial_RxFlag;                                                 // 定义 HEX 接收完成标志，静态存储区变量上电后自动初始化为 0
char Serial_RxTextPacket[SERIAL_TEXT_MAX_LENGTH];                       // 定义文本接收缓冲区，最后会补充 '\0' 形成标准 C 字符串
uint8_t Serial_RxTextFlag;                                             // 定义文本接收完成标志，主循环处理后需要手动清零

void Serial_Init(void)                                                 // 定义 USART1 初始化函数，完成串口收发与接收中断配置
{                                                                      // USART1 初始化函数体开始
    RCC_APB2PeriphClockCmd(RCC_APB2Periph_USART1, ENABLE);              // 开启 USART1 外设时钟，使串口寄存器能够被正常访问
    RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE);               // 开启 GPIOA 时钟，为 PA9 和 PA10 的复用功能配置提供时钟

    GPIO_InitTypeDef GPIO_InitStructure;                               // 定义 GPIO 初始化结构体，用于依次配置发送和接收引脚
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_AF_PP;                     // 将 USART1_TX 配置为复用推挽输出，由串口外设主动驱动高低电平
    GPIO_InitStructure.GPIO_Pin = GPIO_Pin_9;                           // 选择 PA9，对应 STM32F103 默认映射下的 USART1_TX
    GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz;                   // 设置输出速度等级，为串口边沿提供足够的翻转能力
    GPIO_Init(GPIOA, &GPIO_InitStructure);                              // 将上述配置写入 GPIOA 的 PA9 配置寄存器

    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IPU;                       // 将 USART1_RX 配置为上拉输入，使线路空闲或悬空时保持稳定高电平
    GPIO_InitStructure.GPIO_Pin = GPIO_Pin_10;                          // 选择 PA10，对应 STM32F103 默认映射下的 USART1_RX
    GPIO_InitStructure.GPIO_Speed = GPIO_Speed_50MHz;                   // 输入模式下速度字段基本不参与输入逻辑，但保持结构体字段完整
    GPIO_Init(GPIOA, &GPIO_InitStructure);                              // 将上述配置写入 GPIOA 的 PA10 配置寄存器

    USART_InitTypeDef USART_InitStructure;                             // 定义 USART 初始化结构体，用于设置帧格式、波特率和工作模式
    USART_InitStructure.USART_BaudRate = 9600;                          // 将波特率设置为 9600 bit/s，串口助手必须使用相同参数
    USART_InitStructure.USART_HardwareFlowControl = USART_HardwareFlowControl_None; // 关闭 RTS/CTS 硬件流控，只使用 TX 和 RX 两根信号线
    USART_InitStructure.USART_Mode = USART_Mode_Tx | USART_Mode_Rx;     // 同时开启发送器和接收器，以支持双向数据包通信
    USART_InitStructure.USART_Parity = USART_Parity_No;                 // 关闭奇偶校验，使每帧采用常见的 8N1 格式
    USART_InitStructure.USART_StopBits = USART_StopBits_1;              // 设置 1 个停止位，用于标识一个串口字符帧结束
    USART_InitStructure.USART_WordLength = USART_WordLength_8b;         // 设置 8 位数据字长，无校验时每帧携带 8 位有效数据
    USART_Init(USART1, &USART_InitStructure);                           // 根据结构体参数配置 USART1 的控制和波特率寄存器

    USART_ITConfig(USART1, USART_IT_RXNE, ENABLE);                      // 开启接收数据寄存器非空中断，使每收到一个字节就进入中断处理

    NVIC_PriorityGroupConfig(NVIC_PriorityGroup_2);                     // 设置 NVIC 优先级分组，为抢占优先级和响应优先级分配位数
    NVIC_InitTypeDef NVIC_InitStructure;                               // 定义 NVIC 初始化结构体，用于配置 USART1 中断通道
    NVIC_InitStructure.NVIC_IRQChannel = USART1_IRQn;                   // 选择 USART1 全局中断通道，对应 USART1_IRQHandler 函数
    NVIC_InitStructure.NVIC_IRQChannelCmd = ENABLE;                     // 使能 USART1 中断通道，使中断请求能够进入 Cortex-M3 内核
    NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 1;           // 设置抢占优先级为 1，数值越小表示优先级越高
    NVIC_InitStructure.NVIC_IRQChannelSubPriority = 1;                  // 设置响应优先级为 1，用于同抢占级中断的先后仲裁
    NVIC_Init(&NVIC_InitStructure);                                    // 将 USART1 中断优先级配置写入 NVIC 寄存器

    USART_Cmd(USART1, ENABLE);                                         // 最后使能 USART1 外设，使发送、接收和中断逻辑正式开始工作
}                                                                      // USART1 初始化函数体结束
```

### 3. Serial.c：基础发送函数

```c
void Serial_SendByte(uint8_t Byte)                                     // 定义单字节发送函数，为数组、字符串和数据包发送提供统一底层接口
{                                                                      // 单字节发送函数体开始
    USART_SendData(USART1, Byte);                                      // 将待发送字节写入 USART1 数据寄存器，硬件随后自动串行移出
    while (USART_GetFlagStatus(USART1, USART_FLAG_TXE) == RESET);       // 等待发送数据寄存器变空，确保下一字节写入时不会覆盖当前数据
}                                                                      // 单字节发送函数体结束

void Serial_SendArray(uint8_t *Array, uint16_t Length)                  // 定义字节数组发送函数，可发送包含 0x00 在内的任意二进制数据
{                                                                      // 字节数组发送函数体开始
    uint16_t i;                                                        // 定义循环变量，用于依次访问数组中的每一个待发送字节
    for (i = 0; i < Length; i++)                                      // 从数组第 0 个元素循环到 Length - 1，严格按指定长度发送
    {                                                                  // 数组发送循环体开始
        Serial_SendByte(Array[i]);                                     // 调用单字节发送函数，将当前数组元素通过 USART1 发出
    }                                                                  // 数组发送循环体结束
}                                                                      // 字节数组发送函数体结束

void Serial_SendString(char *String)                                   // 定义字符串发送函数，适用于以 '\0' 结尾的 ASCII 文本
{                                                                      // 字符串发送函数体开始
    uint16_t i;                                                        // 定义字符串下标，用于从首字符开始逐字节扫描
    for (i = 0; String[i] != '\0'; i++)                               // 持续发送字符，直到遇到 C 字符串结束符 '\0'
    {                                                                  // 字符串发送循环体开始
        Serial_SendByte((uint8_t)String[i]);                           // 将当前字符转换为无符号字节后交给底层发送函数
    }                                                                  // 字符串发送循环体结束
}                                                                      // 字符串发送函数体结束
```

### 5. USART1_IRQHandler：HEX 数据包接收状态机

```c
void USART1_IRQHandler(void)                                          // 定义 USART1 中断服务函数，本版本专门解析固定长度 HEX 数据包
{                                                                      // USART1 中断服务函数体开始
    static uint8_t RxState = 0;                                       // 定义静态接收状态变量，跨多次中断保存当前解析阶段
    static uint8_t RxIndex = 0;                                       // 定义静态数据下标，记录下一字节应写入接收数组的位置
    uint8_t RxData;                                                    // 定义临时变量，用于保存本次中断从数据寄存器读取的字节

    if (USART_GetITStatus(USART1, USART_IT_RXNE) == SET)                // 判断本次中断是否由接收数据寄存器非空事件触发
    {                                                                  // RXNE 中断处理分支开始
        RxData = (uint8_t)USART_ReceiveData(USART1);                    // 读取接收数据寄存器，取得当前字节并同步清除 RXNE 条件

        if (RxState == 0)                                              // 状态 0 表示当前尚未进入数据包，程序正在等待固定包头
        {                                                              // 等待包头状态处理开始
            if (RxData == 0xFF)                                       // 判断当前字节是否等于约定的 HEX 数据包包头 0xFF
            {                                                          // 正确识别包头后的处理开始
                RxState = 1;                                          // 切换到状态 1，后续字节将作为固定长度数据区保存
                RxIndex = 0;                                          // 将数组下标清零，保证新数据包从接收数组首元素写入
            }                                                          // 正确识别包头后的处理结束
        }                                                              // 等待包头状态处理结束
        else if (RxState == 1)                                        // 状态 1 表示已经收到包头，当前正在接收 4 字节数据区
        {                                                              // 接收数据区状态处理开始
            Serial_RxPacket[RxIndex] = RxData;                         // 将当前字节写入接收数组的指定位置，包头和包尾不会写入数组
            RxIndex++;                                                 // 数据下标自增，为下一次中断保存下一个数据字节做准备
            if (RxIndex >= SERIAL_HEX_DATA_LENGTH)                     // 判断是否已经收满协议规定的 4 字节有效数据
            {                                                          // 固定长度数据区接收完成后的处理开始
                RxState = 2;                                          // 切换到状态 2，下一字节必须是约定的包尾 0xFE
            }                                                          // 固定长度数据区接收完成后的处理结束
        }                                                              // 接收数据区状态处理结束
        else if (RxState == 2)                                        // 状态 2 表示有效数据已经收满，当前正在校验包尾
        {                                                              // 校验包尾状态处理开始
            if (RxData == 0xFE)                                       // 判断当前字节是否等于约定的 HEX 数据包包尾 0xFE
            {                                                          // 正确识别包尾后的处理开始
                Serial_RxFlag = 1;                                    // 置位完整数据包标志，通知主循环可以安全读取接收数组
            }                                                          // 正确识别包尾后的处理结束
            RxState = 0;                                              // 无论包尾正确与否都返回等待包头状态，防止状态机长期卡死
            RxIndex = 0;                                              // 同步清零数据下标，为下一帧数据包接收做好准备
        }                                                              // 校验包尾状态处理结束

        USART_ClearITPendingBit(USART1, USART_IT_RXNE);                 // 调用库函数清除 RXNE 中断挂起标志，保持代码风格完整
    }                                                                  // RXNE 中断处理分支结束
}                                                                      // USART1 中断服务函数体结束
```

### 6. USART1_IRQHandler：文本数据包接收状态机

```c
void USART1_IRQHandler(void)                                          // 定义 USART1 中断服务函数，本版本专门解析以 @ 开头的文本数据包
{                                                                      // USART1 中断服务函数体开始
    static uint8_t RxState = 0;                                       // 定义静态状态变量，0 等待包头、1 接收文本、2 等待换行符
    static uint8_t RxIndex = 0;                                       // 定义静态文本下标，记录下一字符应写入缓冲区的位置
    uint8_t RxData;                                                    // 定义临时变量，用于保存本次串口中断接收到的字符

    if (USART_GetITStatus(USART1, USART_IT_RXNE) == SET)                // 判断 USART1 是否因收到一个新字节而触发 RXNE 中断
    {                                                                  // RXNE 中断处理分支开始
        RxData = (uint8_t)USART_ReceiveData(USART1);                    // 读取当前接收字符，并通过读数据寄存器完成 RXNE 事件响应

        if (RxState == 0)                                              // 状态 0 表示当前不在数据包内，程序只寻找文本包头
        {                                                              // 等待文本包头状态处理开始
            if (RxData == '@')                                        // 判断当前字符是否为约定的文本包头字符 '@'
            {                                                          // 正确识别文本包头后的处理开始
                RxState = 1;                                          // 切换到文本接收状态，从下一字符开始保存命令内容
                RxIndex = 0;                                          // 清零文本下标，避免上一帧残留位置影响新命令
            }                                                          // 正确识别文本包头后的处理结束
        }                                                              // 等待文本包头状态处理结束
        else if (RxState == 1)                                        // 状态 1 表示已经收到 '@'，当前正在接收命令正文
        {                                                              // 接收命令正文状态处理开始
            if (RxData == '\r')                                       // 判断当前字符是否为回车符，回车符是 CRLF 包尾的第一部分
            {                                                          // 收到回车符后的处理开始
                RxState = 2;                                          // 切换到状态 2，要求下一字符必须为换行符 '\n'
            }                                                          // 收到回车符后的处理结束
            else if (RxIndex < SERIAL_TEXT_MAX_LENGTH - 1)             // 判断缓冲区是否仍有空间，并为结尾的 '\0' 预留一个字节
            {                                                          // 文本缓冲区仍有空间时的处理开始
                Serial_RxTextPacket[RxIndex] = (char)RxData;           // 将当前普通字符写入文本缓冲区，不保存包头和包尾
                RxIndex++;                                             // 文本下标自增，使下一字符写入缓冲区的后续位置
            }                                                          // 文本缓冲区仍有空间时的处理结束
            else                                                       // 当文本长度超过缓冲区容量时进入异常恢复分支
            {                                                          // 文本缓冲区溢出处理开始
                RxState = 0;                                          // 放弃当前超长数据包并返回等待包头状态，防止数组越界
                RxIndex = 0;                                          // 清零文本下标，为下一条合法命令重新开始接收
            }                                                          // 文本缓冲区溢出处理结束
        }                                                              // 接收命令正文状态处理结束
        else if (RxState == 2)                                        // 状态 2 表示已经收到 '\r'，当前等待 CRLF 的第二个字符
        {                                                              // 等待换行符状态处理开始
            if (RxData == '\n')                                       // 判断当前字符是否为换行符，确认完整收到 "\r\n" 包尾
            {                                                          // 正确识别文本包尾后的处理开始
                Serial_RxTextPacket[RxIndex] = '\0';                   // 在文本末尾补充字符串结束符，使缓冲区成为合法 C 字符串
                Serial_RxTextFlag = 1;                                // 置位文本包接收完成标志，通知主循环可以解析命令
            }                                                          // 正确识别文本包尾后的处理结束
            RxState = 0;                                              // 无论换行符是否正确都返回等待包头状态，重新同步下一帧
            RxIndex = 0;                                              // 清零文本下标，避免下一帧沿用本次命令的长度
        }                                                              // 等待换行符状态处理结束

        USART_ClearITPendingBit(USART1, USART_IT_RXNE);                 // 清除 USART1 的 RXNE 中断挂起状态，完成本次中断处理
    }                                                                  // RXNE 中断处理分支结束
}                                                                      // USART1 中断服务函数体结束
```

```c
        {                                                              // 完整 HEX 数据包处理分支开始

            }                                                          // 接收数据显示循环体结束
        }                                                              // 完整 HEX 数据包处理分支结束
    }                                                                  // 主循环体结束，程序会继续从 while 条件处重复运行
}                                                                      // 主函数体结束，嵌入式程序正常情况下不会执行到此函数返回
```

## 关键知识点

### 1. 为什么串口通信需要数据包

#### 原理

USART 硬件只负责按位发送和接收字节流。对于硬件而言，连续到达的字节本身没有“第几条命令”或“哪一帧数据”的概念。

应用层必须自行约定包头、数据区、长度、包尾等规则，接收端才能从连续字节流中恢复出独立消息。

#### 特点

- 数据包为连续字节增加边界。
- 接收端可以判断数据是否完整。
- 一帧可以同时携带多个参数。
- 协议格式由通信双方共同约定。
- 简单串口协议通常由状态机解析。

#### 面试易问

**Q：USART 能否自动识别应用层数据包？**

A：不能。USART 外设负责字符帧的起始位、数据位、校验位和停止位，但不知道应用层的一条命令由多少个字符组成。应用程序需要自行设计并解析数据包。

**Q：串口字符帧与应用层数据包有什么区别？**

A：字符帧是 USART 硬件发送一个字节时的位级格式；应用层数据包由多个字符帧组成，用于表达一条完整消息。

#### 易错点

- 把“收到一个字节”误认为“收到一帧完整业务数据”。
- 不设计帧边界，导致粘包后无法区分多条消息。
- 发送端和接收端使用不同的数据区长度。
- 在中断中直接执行复杂业务，造成后续字节来不及接收。

---

### 2. HEX 数据包

#### 原理

HEX 数据包直接传输二进制字节。本实验使用 `0xFF` 作为包头、4 字节固定数据区、`0xFE` 作为包尾。

串口助手的 HEX 显示只是把每个字节以十六进制形式展示，线路上传输的仍然是二进制位。

#### 特点

- 数据紧凑，传输效率高。
- 可以直接表达 0～255 的字节值。
- 不便于人直接阅读。
- 必须明确字段长度、字节序和数据类型。
- 适合传感器数据、控制参数和设备间通信。

#### 面试易问

**Q：发送字节 `0x41` 与发送文本 `"41"` 有什么区别？**

A：`0x41` 只发送一个字节，其数值为 65；文本 `"41"` 会发送字符 `'4'` 和 `'1'` 两个字节，对应 ASCII 编码 `0x34` 和 `0x31`。

**Q：为什么 HEX 数据包通常比文本数据包效率高？**

A：同一个数值使用二进制编码所需字节更少，也不需要十进制转字符串和字符串再转数值的过程。

#### 易错点

- 串口助手处于文本模式，却输入 `FF 01 02 03 04 FE`，实际发送的是字符。
- 把十六进制显示格式误认为线路上存在“十六进制字符”。
- 多字节整数没有约定高字节在前还是低字节在前。
- 将有符号数、无符号数或浮点数直接传输，却没有统一数据表示方式。

---

### 3. 文本数据包

#### 原理

文本数据包将命令编码为 ASCII 字符。本实验通过 `@` 标记数据开始，通过 `\r\n` 标记数据结束，并在接收缓冲区末尾补充 `\0`。

例如：

```text
线路字节：40 4C 45 44 5F 4F 4E 0D 0A
文本含义：@  L  E  D  _  O  N  \r \n
```

#### 特点

- 人可以直接阅读和输入。
- 调试方便，适合命令行和配置接口。
- 数据长度通常可变。
- 相同信息占用的字节通常多于二进制协议。
- 解析时需要处理字符串结束符、大小写和格式。

#### 面试易问

**Q：为什么接收完成后需要手动写入 `\0`？**

A：串口接收到的数据只是普通字节数组。C 字符串函数依靠 `\0` 判断字符串结束，因此必须预留空间并在命令末尾补充结束符。

**Q：`\r` 和 `\n` 分别是什么？**

A：`\r` 是回车字符，ASCII 值为 `0x0D`；`\n` 是换行字符，ASCII 值为 `0x0A`。许多文本协议使用连续的 CRLF 作为行结束标志。

#### 易错点

- 串口助手没有开启“发送新行”或只发送了 `\n`。
- 输入了可见字符 `\`、`r`、`\`、`n`，而不是控制字符 CRLF。
- 接收数组末尾没有补 `\0` 就调用 `strcmp()`。
- 缓冲区太小，长命令造成数组越界。

---

### 4. 串口接收状态机

#### 原理

状态机把数据包解析过程拆分为有限状态：

```text
状态 0：等待包头
状态 1：接收数据区
状态 2：等待或校验包尾
状态完成：置位接收标志并回到状态 0
```

每次 RXNE 中断只输入一个字节。状态机依据当前状态和新字节决定保存数据、切换状态或放弃当前帧。

#### 特点

- 每次中断处理时间短。
- 能够跨多次中断保存解析进度。
- 逻辑清晰，便于扩展协议。
- 遇到错误包尾时可以重新同步。
- 适合没有操作系统的裸机程序。

#### 面试易问

**Q：为什么状态变量通常声明为 `static`？**

A：中断函数每次进入都需要知道上一次处理到了哪一步。静态局部变量的生命周期贯穿整个程序，退出函数后数值不会丢失。

**Q：状态机相比连续 `if` 判断有什么优势？**

A：状态机明确限定每个阶段允许接受的输入，能够保存上下文并控制状态转移，复杂协议更容易维护和排错。

#### 易错点

- 状态变量不是静态变量，每次中断都重新变为 0。
- 数据包错误后没有回到初始状态，后续数据全部无法解析。
- 数组下标未清零，下一帧从错误位置继续写入。
- 状态机中执行 OLED 刷新、延时或字符串打印，导致中断处理过慢。

---

### 5. 固定长度与可变长度协议

#### 原理

固定长度协议通过预先约定的数据区长度判断何时接收完毕；可变长度协议通常依靠长度字段或结束符确定数据区结束。

HEX 示例的数据区固定为 4 字节；文本示例的数据区长度可变，以 `\r\n` 结束。

#### 特点

| 类型 | 优点 | 缺点 |
|---|---|---|
| 固定长度 | 解析简单、时间确定、无需搜索结束符 | 长度不灵活，短消息也占固定空间 |
| 结束符协议 | 长度灵活、适合文本命令 | 数据区包含结束符时需要转义 |
| 长度字段协议 | 可传输任意二进制数据、边界明确 | 必须防止长度字段错误导致越界 |

#### 面试易问

**Q：二进制协议为什么更常使用长度字段，而不是只使用包尾？**

A：二进制数据可能包含任意字节值，也可能与包尾相同。长度字段允许接收端按明确数量读取数据，不会把数据内容误判为帧结束。

**Q：固定长度协议是否还需要包尾？**

A：不是绝对需要，但包尾可以提供额外的结构校验与同步依据。本实验保留包尾用于帮助理解完整的数据包格式。

#### 易错点

- 改变数组长度后没有同步修改协议宏。
- 可变长度协议没有设置最大长度。
- 接收到异常长度字段后直接信任并写入数组。
- 使用结束符协议传输原始二进制数据，却没有转义机制。

---

### 6. 中断与主循环之间的数据交接

#### 原理

中断负责快速接收字节并写入缓冲区，完整一帧后置位标志；主循环看到标志后再解析命令、刷新 OLED 或控制 LED。

这种方式把实时性要求高的字节接收与耗时业务处理分离。

#### 特点

- 中断函数短小。
- 主循环逻辑更容易调试。
- 接收标志相当于简单事件通知。
- 缓冲区由中断写、主循环读。
- 高速或连续数据下可进一步使用环形缓冲区或 DMA。

#### 面试易问

**Q：为什么不建议在 USART 中断中直接调用 `OLED_ShowString()`？**

A：OLED 通信通常较慢，会显著延长中断占用时间。此时新的串口字节可能到达并引发溢出，应在中断中置标志后交给主循环处理。

**Q：中断与主循环共享变量为什么常使用 `volatile`？**

A：`volatile` 告诉编译器该变量可能在当前执行流之外被修改，避免编译器把变量值长期缓存。不过它不能自动保证多字节访问的原子性。

#### 易错点

- 主循环处理后忘记清接收完成标志。
- 中断在主循环读取数组时立即开始覆盖下一帧。
- 将 `volatile` 误认为线程安全或原子操作。
- 数据流较快时仍使用单缓冲区，造成新旧数据竞争。

---

### 7. 文本命令解析

#### 原理

接收状态机将命令正文保存为以 `\0` 结尾的字符串，主循环通过 `strcmp()` 与预定义命令逐一比较。

```c
strcmp(Serial_RxTextPacket, "LED_ON") == 0
```

返回值为 0 表示两个字符串内容完全相同。

#### 特点

- 代码直观，适合少量固定命令。
- 命令可以包含字母、数字和分隔符。
- 可通过响应包反馈执行结果。
- 命令数量增加后可使用命令表或解析器。
- 参数命令可进一步使用 `sscanf()` 或自定义分词。

#### 面试易问

**Q：`strcmp()` 返回 0 为什么表示相等？**

A：该函数返回两个字符串第一个不同字符的差值；如果所有字符相同并同时遇到 `\0`，差值为 0。

**Q：大量命令都使用 `if...else if` 有什么问题？**

A：代码会变长且难维护。可建立“命令字符串—处理函数”映射表，遍历匹配后调用对应回调函数。

#### 易错点

- 写成 `if (strcmp(...))`，结果在不相等时反而进入分支。
- 命令中混入空格、CR、LF 或大小写差异。
- OLED 上看到文字正确，但缓冲区末尾仍有旧数据。
- 使用 `==` 比较两个字符串指针，而不是比较字符串内容。

---

### 8. 简单协议的可靠性改进

#### 原理

本节协议主要用于教学，只能判断包头、数据长度和包尾。真实项目中还应考虑数据损坏、丢字节、重复帧、超时和缓冲区竞争。

常见增强字段如下：

```text
包头 + 版本 + 命令 + 长度 + 序号 + 数据 + CRC/校验和 + 包尾
```

#### 特点

- 长度字段支持可变长二进制数据。
- 校验和或 CRC 可检测传输错误。
- 序号可识别重复包和丢包。
- 超时机制可从半包状态恢复。
- 转义机制可避免数据区与控制字节冲突。

#### 面试易问

**Q：校验和与 CRC 的主要作用是什么？**

A：它们用于检测数据在传输过程中是否发生错误。CRC 对常见突发错误的检测能力通常强于简单累加和。

**Q：状态机收到包头后一直收不到包尾怎么办？**

A：应增加接收超时。超过允许时间后清空下标并返回等待包头状态，避免状态机永久停留在半包状态。

#### 易错点

- 把教学协议直接用于高可靠性产品。
- 只检查包尾，不校验数据内容。
- 未限制声明长度，恶意或错误数据造成数组越界。
- 没有超时，线路中断后状态机无法自动恢复。

## 本节核心记忆

```text
USART 只提供连续字节流，数据包边界必须由应用层协议定义。
```

```text
HEX 数据包：紧凑高效，适合设备通信，但必须约定长度、类型和字节序。
文本数据包：直观易调试，适合命令交互，但占用字节更多。
```

```text
接收状态机 = 当前状态 + 新字节 → 保存数据 / 切换状态 / 完成一帧。
```

```text
中断负责快速收字节和置标志，主循环负责解析命令与执行耗时业务。
```

```text
C 字符串必须以 '\0' 结束；CRLF 包尾由 '\r' 和 '\n' 两个控制字符组成。
```

## 开发过程总结

### 问题 1：串口助手发送数据后，STM32 完全没有反应

现象：

- OLED 接收区域不更新
- 接收完成标志始终为 0
- USART1 中断函数没有进入

排查过程：

1. 检查 USB-TTL 的 TX 是否连接 PA10
2. 检查 USB-TTL 的 RX 是否连接 PA9
3. 检查 USB-TTL 与 STM32 是否共地
4. 检查两端波特率和 8N1 配置是否一致
5. 检查是否开启 USART1、GPIOA 和 NVIC 时钟/中断
6. 在中断函数中设置断点，确认 RXNE 是否触发

解决方案：

- 交换 TX 和 RX 接线
- 补接公共 GND
- 将串口助手设置为 9600、8N1、无流控
- 确认调用 `USART_ITConfig(USART1, USART_IT_RXNE, ENABLE)`

### 问题 2：HEX 数据包一直不能完成接收

现象：

- 单个字节可以进入中断
- `Serial_RxFlag` 始终没有置 1
- OLED 不显示完整的 4 字节数据

排查过程：

1. 检查串口助手是否处于 HEX 发送模式
2. 检查发送内容是否严格为 6 字节
3. 检查包头是否为 `FF`
4. 检查数据区是否恰好为 4 字节
5. 检查包尾是否为 `FE`
6. 观察状态变量是否按 0 → 1 → 2 → 0 变化

解决方案：

- 使用 `FF 01 02 03 04 FE` 进行最小测试
- 不要在固定 4 字节数据区中漏发或多发字节
- 保证 `SERIAL_HEX_DATA_LENGTH` 与发送端协议一致

### 问题 3：文本命令显示正确，但 LED 不动作

现象：

- OLED 可以显示 `LED_ON`
- `strcmp()` 判断始终不成立
- 程序返回 `ERROR_COMMAND`

排查过程：

1. 检查字符串末尾是否补充 `\0`
2. 检查命令是否包含空格
3. 检查字母大小写是否一致
4. 检查 CRLF 是否已经从正文中排除
5. 使用调试器查看数组中每个字符的 ASCII 值

解决方案：

- 在确认 CRLF 完整后执行 `Serial_RxTextPacket[RxIndex] = '\0'`
- 串口助手只发送 `@LED_ON` 并追加 CRLF
- 统一命令大小写和下划线格式

### 问题 4：发送 `@LED_ON` 后状态机不结束

现象：

- 状态机进入文本接收状态
- 完成标志不置位
- 后续命令也无法正常识别

排查过程：

1. 检查串口助手是否追加 CRLF
2. 检查程序是否先判断 `\r` 再判断 `\n`
3. 检查串口助手是否只追加 LF
4. 观察接收字节是否出现 `0D 0A`

解决方案：

- 将串口助手行尾设置为 CRLF
- 或手动发送字节 `40 4C 45 44 5F 4F 4E 0D 0A`
- 若上位机只发送 LF，应同步修改协议和状态机

### 问题 5：连续发送长文本后程序异常

现象：

- OLED 显示乱码
- 程序进入 HardFault
- 后续命令无法识别

排查过程：

1. 检查 `RxIndex` 是否可能超过数组长度
2. 检查是否为 `\0` 预留位置
3. 检查异常超长包后状态机是否复位
4. 检查主循环和中断是否同时访问同一缓冲区

解决方案：

- 写入前判断 `RxIndex < SERIAL_TEXT_MAX_LENGTH - 1`
- 超长时立即放弃当前帧并清零状态
- 高速连续接收时改用双缓冲或环形缓冲区

### 问题 6：LED 控制逻辑与命令相反

现象：

- 发送 `LED_ON` 后 LED 熄灭
- 发送 `LED_OFF` 后 LED 点亮

排查过程：

1. 查看 LED 的硬件连接方式
2. 确认 LED 是高电平还是低电平点亮
3. 检查 `LED1_ON()` 和 `LED1_OFF()` 的底层实现
4. 不要只根据 `GPIO_SetBits()` 函数名判断亮灭

解决方案：

- 在 LED 模块内部统一封装有效电平
- 若 LED 为低电平点亮，则 `LED1_ON()` 应输出低电平
- 主函数只调用语义明确的 LED 接口，不直接操作 GPIO

## 结果展示

> 实验 1：按下按键后，STM32 按 `FF + 4 字节数据 + FE` 的格式发送 HEX 数据包，串口助手可观察到数据区随按键逐次变化。✅

> 实验 2：串口助手以 HEX 模式发送 `FF 01 02 03 04 FE` 后，STM32 的接收状态机完成一帧解析，OLED 显示 `01 02 03 04`。✅

> 实验 3：串口助手发送 `@LED_ON\r\n` 后，STM32 点亮 LED，并返回 `@LED_ON_OK\r\n`。✅

> 实验 4：串口助手发送 `@LED_OFF\r\n` 后，STM32熄灭 LED，并返回 `@LED_OFF_OK\r\n`。✅

> 实验 5：发送未定义命令时，程序不执行 LED 操作，并返回 `@ERROR_COMMAND\r\n`。✅

## 本节小结

本节在基础 USART 字节收发之上增加了应用层协议，完成了 HEX 数据包和文本数据包的发送、接收与解析。

最重要的知识点是：

```text
连续字节流本身没有消息边界，必须使用包头、长度、包尾或结束符划分数据包。
```

HEX 数据包适合高效率的设备间数据传输；文本数据包适合人机交互、配置命令和调试接口。无论采用哪种格式，都可以通过接收状态机逐字节解析，并在完整一帧后把业务处理交给主循环。
